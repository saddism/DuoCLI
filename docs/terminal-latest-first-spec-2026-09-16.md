# 会话切换即显最新、历史按需加载 Spec

日期：2026-09-16  
状态：研究与设计；尚未实施或完成运行时验收。  
范围：Electron 桌面终端、手机/PWA 终端及其共享 PTY 服务。本文只新增文档，不修改业务代码。

## 1. 决策与用户体验

采纳“进入就看最新，往上翻才加载历史”。切换会话后，第一幅可读画面应直接位于最新输出，不播放从旧内容滚到末尾的过程。历史加载不得重置正在阅读的画面，也不得打断正在运行的 CLI。

“不刷新”指不出现清屏、历史重放、滚动追赶和重复重建的可见过程；正常的新输出仍持续更新。冷连接存在网络和解析耗时，不能承诺所有网络下零等待。

推荐分两阶段实现：先修复两端首次呈现和现有历史入口，再实现独立的历史分页阅读层。桌面已驻留且跟上输出的终端继续复用，不为统一形式强制重新拉快照。

## 3. 为什么会“从上面刷很久”

终端接收的是绘制指令流，包含文字、光标移动、擦除、颜色、进度动画和屏幕切换。回放原始输出相当于重新执行绘制过程；最后执行一次跳底只能调整最终位置，无法消除前面的解析耗时。[xterm 官方 API](https://xtermjs.org/docs/api/terminal/classes/terminal/) 明确 `write()` 异步解析，必须等回调才能读取完成后的 buffer。

可能叠加的原因，按运行时排查顺序：

1. 实际客户端或服务仍运行较早代码，手机未走最新屏快照，或快照失败进入 raw fallback。
2. 桌面隐藏终端积压 write；切回来后解析追赶，并随每批输出跟尾。此为待测假设，当前代码只能证明持续写入。
3. 画布在定位完成前可见，挂载、fit、横幅高度或延迟定位导致多次可见变动。
4. 手机和电脑列宽不同，PTY resize 使 CLI 自己重新输出界面。它看起来像历史回放，但来源是新生成的输出。
5. 历史加载 reset/rewrite 累计快照，造成清屏或等待；在新输出同时到达时，“距底多少行”也不是稳定的阅读锚点。

必须用 trace 区分以上来源，不能把两端归为一个未经验证的根因。

## 4. 必须解决的冲突

| 冲突 | 决策 |
| --- | --- |
| 最新屏加载快，但终端状态依赖前文 ANSI | 使用已解析状态快照；禁止随意截最后 N 字节作为正确性方案 |
| 默认看最新，但用户正在翻旧内容 | 显式从会话列表进入跟尾；同一会话内上滚、选区、窗口变化和短暂后台恢复保持阅读意图 |
| 历史往前补，live 流还在更新 | 历史分页不写入 live xterm；使用固定历史锚点，live 在后台继续接收 |
| 手机窄、桌面宽，共享 PTY 只有一个尺寸 | 沿用单一尺寸所有者；一次打开合并有效尺寸提交，非所有者本地排版不反复调整 PTY |
| 终端不是聊天消息列表 | v1 分页的是已滚出正常屏幕的可读终端行，不推断问答轮次，不把绘制指令当消息 |
| 少加载和完整保留不是一回事 | 首屏不加载不等于删除历史；分页仅覆盖明确保留的数据，不声称无限历史 |

## 5. 交互规则

- 从列表进入或显式重新选择会话：立即定位最新，关闭之前的历史阅读状态；桌面点击当前 pane 内选字不视为重新选择。
- 热终端：完成本地布局和瞬时定位后显示；不销毁终端、重启 PTY或重新执行 CLI resume。
- 冷终端：获取最新屏，离屏恢复并完成定位，再一次显示。超过 150ms 才显示轻量“正在连接…”占位，禁止旧会话内容冒充新会话。
- 用户向更早内容滚动时，已有本地内容立即可读；接近已加载上边界后请求一页。没有本地历史时，第一下明确的向历史方向手势也必须触发，不依赖 viewportY 实际变化。
- 历史加载中保留当前画面，只在顶部显示小提示。单会话单个在途请求；失败保留位置并可重试，不自动无限重试。
- 回看时新输出不拉回底部；显示“有新输出 · 回到最新”。点击后切换至后台一直维护的最新终端，瞬时跟尾。
- 选区、复制、链接和用户输入摘要跳转保持可用。跳转目标不在已加载范围时，按锚点取附近历史；找不到时明确提示，不能无反馈。
- 空会话是合法状态：等待 live，不通过反复订阅来制造首屏。会话退出、网络断开分别提示，不写入伪造的历史输出。
- 缓冲区为 alternate screen 时，滚动按当前程序的交互语义处理；不自动往其内部插入正常屏历史。可从明确的历史入口查看此前正常屏内容。[终端模式说明](https://xtermjs.org/docs/api/vtfeatures/)

## 6. 第一阶段：最新画面一次呈现

### 6.1 桌面

优先修复驻留实例路径：挂载时使用有效的目标区域尺寸；在用户看到画布之前完成必要 fit 和瞬时跳底；避免无尺寸变化的重复 resize。不要用固定 50ms 定时器作为“已完成”的依据。

为输出记录接收/解析水位及等待时长。若实测存在后台积压，添加有界恢复路径：隐藏期间不无限累积 renderer 原始输出；实例标记需重同步，重新可见时使用主进程最新屏快照恢复。切换恢复期间的输入和 live 尾部必须遵守序号边界。不能直接清掉 write 队列后从任意 ANSI 字节继续。

新增桌面快照能力时，IPC 与 WebSocket 复用同一状态服务。跨端尺寸不同必须验证快照等价性，不能把按桌面列宽生成的屏幕直接当作手机列宽的完整状态。

### 6.2 手机

保留最新屏快照基础，修复无 scrollback 时的上滚入口；加载只由明确的历史意图触发，初次布局、程序滚动和普通点击不能提前请求历史。

快照恢复应先按源 cols/rows 还原，再在显示前应用目标尺寸策略。本地安装的 `@xterm/addon-serialize/typings/addon-serialize.d.ts` 建议在同尺寸终端恢复后再 resize，并建议避免渲染未完成帧。改动前需用现有手机几何兼容案例验证，不能简单删除现有特殊处理。

遮罩必须等解析完成、正确定位且目标帧可呈现后才退出；不能仅凭收到了 replay 或首个 output 就揭开。所有回调校验会话/连接代次，旧会话完成回调不得改变新会话 loading 状态。

### 6.3 快照与增量一致性

恢复响应增加或统一：`sessionId`、`subscriptionId`、`requestId`、`epoch`、`geometryRevision`、`sequence`、`cols`、`rows`、`data`、历史边界和能力版本。

快照 S 与之后输出属于同一有序状态队列；S 已包含的输出不重放；S 之后的输出完整排队。批量输出使用明确的 `fromSequence/toSequence`，不要假设每个消息序号只增加 1。接收水位与已应用水位分离，解析成功后才推进后者。会话重建导致 epoch 改变必须重新同步。

输出积压超过预算时重新取紧凑状态，不把缺失的一段原始 ANSI 当作可以忽略。快照失败显示可重试状态；兼容性 raw 回退必须显式标记并离屏完成，不伪称“已加载全部历史”。

## 7. 第二阶段：真正的历史分页

### 7.1 推荐结构

主进程继续维护权威 live terminal；另外保存正常缓冲区滚出的可读逻辑行。客户端历史层只读、虚拟列表渲染，放在原终端区域内；用户无需打开新的页面。live xterm 在后台继续运行，回到最新时直接展示。

当前 `80 → 160 → 240` 行累计快照可作为第一阶段过渡，但不满足最终“不重放已加载历史”的验收。xterm 的 ANSI write 是执行终端操作，不能用它直接向顶部安全插入普通历史分页。

### 7.2 历史数据与保留范围

每条逻辑行包含稳定 `lineId`、`epoch`、文字与受支持的样式 runs、换行/软换行信息、来源顺序及修订信息。超链接仅保留经过现有安全规则处理的目标；历史层不执行 OSC/CSI 指令。

捕获的是进入 scrollback 的正常屏内容，不是每一帧光标重绘。第一项技术验证是证明捕获在连续输出、reflow、清屏和缓冲区淘汰下无遗漏/重复；若使用 xterm 内部接口必须封装并锁定版本。当前项目没有这套稳定行档案，不能视作现成能力。

历史初始保留预算按现有服务端 5000 物理行等价容量设计，并新增字节硬上限，具体值通过样本测量确定。不得因接入新协议直接缩减桌面已有 10000 行可读内容：驻留的旧内容继续可读；切换到统一保留策略需显式标出边界。v1 不新增磁盘持久化，不承诺恢复早已被淘汰的行或整个 CLI 会话记录。

### 7.3 分页协议

请求：`historyBefore({ sessionId, epoch, requestId, beforeCursor, limitRows: 80 })`。游标绑定首次回看的历史视图版本；响应包含 `items`、`nextCursor`、`hasMore`、`earliestAvailable`、`truncated`。行数与编码字节双重限额；超长逻辑行使用可续传片段，不能无限大或静默截断。

新增输出不会改变已发分页的行标识或插入顺序。到达保留边界显示“更早内容已不在本次终端缓存中”。过期游标返回明确结果，不伪装成正常空页。

快照同时返回与历史层衔接的稳定边界。进入回看时固定最新侧的阅读切片；之后 live 输出留在实时层，不挤动阅读层。历史与最新侧重叠按 lineId 去重；未提交的屏幕行需视图版本标识，不能仅用文本去重（相同日志可以合法重复）。

### 7.4 阅读锚点

以“顶部可见 lineId + 逻辑行内字符位置 + 像素偏移”定位，分页 prepend 后还原同一内容。不能仅保存 viewportY 或距底行数；这些值会随新输出和列宽变化而漂移。

分页期间用户继续滚动，以提交时最新的手势和锚点为准；用户已回到底部或切换会话时不强行进入历史。窗口缩放、字体变化和软键盘高度变化后用同一内容锚点重新定位。

历史文字选择跨页时暂缓回收涉及的行，设置合理选择范围上限并提示；虚拟列表不能悄悄丢选区。用户输入摘要 marker 需要映射到稳定行标识，单靠当前 xterm 行号不够。

## 8. 性能目标与可观测性

以下为待验收目标，不是已测结果。统一记录 `switchStart → snapshotRequested → snapshotReceived → parsed → positioned → firstLatestPaint`，附客户端构建号、服务端版本、SW 版本、设备、会话代次、数据字节数、队列等待、resize 次数及 fallback 原因。指标不记录对话正文。

| 场景 | 目标 |
| --- | --- |
| 桌面已同步的驻留实例，稳定尺寸 | 点击到最新可读画面 P95 ≤ 100ms |
| 手机连接就绪、局域网正常、主进程无明显积压 | 点击到最新可读画面 P95 ≤ 300ms |
| 冷连接/公网 | 分开统计连接耗时；拿到完整最新快照后到呈现 P95 ≤ 100ms，不承诺整体固定耗时 |
| 首屏 | 用户未回看前历史请求数为 0；无可见中间历史帧；恢复一次有效画面 |
| 第二阶段分页 | 只传本页新增内容；正常固定尺寸下阅读锚点偏移 ≤ 1 像素；失败不清空当前内容 |

快照传输/客户端解析量应随当前屏幕大小受限，而不是随保留历史线性增加。但主进程仍需解析全部 PTY 输出以维护正确状态；最新屏方案不会让这一成本消失，也不会自动缩短 CLI 自己的恢复时间。若 headless 队列成为瓶颈，需要单独的批处理/背压优化。[xterm 流控指导](https://xtermjs.org/docs/guides/flowcontrol/)

## 9. 验收与交付顺序

1. 建立运行时基线：同一长会话，记录手机、桌面各至少 30 次冷热切换；同时记录真实构建版本、网络、帧录像、输出水位和 resize 来源。确认用户描述属于哪条路径。
2. 第一阶段完成：验证长日志、持续 spinner/TUI、空会话、手机首屏零历史上滚、rapid A→B→A、分页中切换、断线重连、PWA 前后台和桌面 pane 挂载。
3. 分页捕获验证：使用确定性终端输出，对比完整解析基准与分页拼接结果；覆盖重复文字、中文宽字符、emoji、超长软换行、清屏、alternate buffer、5000 行淘汰及 resize。无法证明无缺行时不得发布第二阶段。
4. 双端竞争验证：手机打开/关闭、键盘展开、桌面缩放、多 pane 同时输出；没有重复尺寸争夺，无跨会话脏回调，无输出丢失或重复，阅读不被新输出抢走。
5. 交互回归：标题/用户输入摘要定位、文件链接、复制、跨页选择、回到最新、CLI 输入模式与粘贴。采用真实生产 DOM/CSS；浏览器模拟不能代替 Android/iOS 和 Electron 实际录像。
6. 按能力版本灰度：服务端先支持新协议；兼容旧客户端；手机 SW 与脚本版本一致。关闭新历史层可回退旧阅读方式，但不重启 PTY、不删除历史。实际发布属于后续实施范围。

最终交付需分别报告：代码完成、针对性测试、浏览器/Electron 测试、真实手机证据和安装/服务版本。第一阶段达到“切换不刷屏”不能宣称第二阶段的真正分页已经完成。

## 10. 预期收益与边界

手机冷进入长会话、桌面确认存在后台积压的会话，预计收益最大：避免客户端执行大量历史绘制，减少网络传输及可见重排。桌面已同步的驻留实例主要收益来自呈现时机和尺寸稳定，不能套用“下载历史少所以快”的解释。

用户得到的默认体验是“看最新 → 主动往前翻 → 留在正在读的内容 → 一下回到最新”。完整的分页层工作量大于修改 scrollToBottom，但它才能解决历史越翻越重、重写 live 状态和阅读位置漂移之间的冲突。
